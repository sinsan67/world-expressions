2 Skills Claude Code créés Fait

Schéma PostgreSQL conçu Fait

5 tables définies pour gérer le multilingue réel : expressions dans leur langue d'origine, contenu traduit séparé, concepts cross-langue, tags normalisés. Schéma évolutif pensé pour des dizaines de langues.

PostgreSQL local installé + schéma déployé Fait

Postgres.app installé sur Mac. Base expressions_dev créée. SQLAlchemy + Alembic mis en place. Première migration appliquée : les 6 tables existent dans PostgreSQL local.

Décisions d'architecture prises
Base de données
PostgreSQL
Unicode natif, FTS multilingue, scalable. SQLite abandonné car incompatible avec la vision multilingue et volumineuse.
Frontend
Next.js + TypeScript
Router fichier-système, SSR pour le SEO, SVG cliquables natifs. TypeScript pour la robustesse sur un schéma de données précis.
ORM / Migrations
SQLAlchemy + Alembic
Schéma défini en Python, migrations versionnées. Même code pour la base locale et Supabase (prod).
Hébergement cloud
Supabase (à créer)
PostgreSQL hébergé gratuit (500MB), dashboard visuel pour browsing des données, facile à connecter via DATABASE_URL.
Recherche
Meilisearch (à venir)
Pour la recherche multilingue à grande échelle avec typos et accents. PostgreSQL LIKE insuffisant avec beaucoup de langues.
Skills Claude Code
Commandes slash métier
Pas d'agents experts (= overhead inutile en solo). Des skills concrets : /validate-db, /add-expression, /generate-expressions à venir.
Schéma de données — les 5 tables
Principe clé : le texte d'une expression ("Avoir le cafard") ne se traduit jamais — c'est un artefact culturel. Seul le contenu explicatif (sens, origine, exemple) est traduit, dans expression_content.
CONCEPTS ← l'idée abstraite cross-langue id UUID slug TEXT "sadness-melancholy" EXPRESSIONS ← l'expression dans sa langue d'origine id TEXT "avoir-le-cafard" text TEXT "Avoir le cafard" ← jamais traduit language TEXT "fr" | "en" | "es" | "ar" | "zh"... region TEXT "fr" | "gb" | "us"... register TEXT informal | standard | slang | vulgar | formal illustration TEXT URL ou SVG (null pour l'instant) concept_id UUID? → CONCEPTS (nullable) EXPRESSION_CONTENT ← contenu traduit (1 ligne par langue) expression_id TEXT → EXPRESSIONS locale TEXT "fr" | "en" | "es"... meaning TEXT origin TEXT example TEXT TAGS ← tags normalisés, indépendants de la langue id TEXT "animals" slug TEXT TAG_NAMES ← nom du tag dans chaque langue tag_id TEXT → TAGS locale TEXT "fr" → "animaux" | "en" → "animals" name TEXT + expression_tags (jointure many-to-many)

Prochaines étapes
Ce que tu fais toi

Créer le compte Supabase Action requise

1. Va sur supabase.com → "Start your project"
2. Crée un compte (GitHub ou email)
3. "New project" → nom : expressions-du-monde
4. Région : Europe West (Frankfurt)
5. Génère un mot de passe fort et note-le
6. Une fois créé, va dans Settings → Database → copie l'URI de connexion (commence par postgresql://...)
7. Donne cette URL à Claude dans la prochaine session

Finir d'ajouter la nouvelle langue dans le JSON En cours

Continuer l'enrichissement de data/expressions.json avec les nouvelles expressions. Elles seront migrées vers PostgreSQL automatiquement.

Ce que Claude fait (prochaine session)

Écrire le script de migration JSON → PostgreSQL

Lit expressions.json, insère dans les nouvelles tables : expressions + expression_content + tags normalisés. Toutes les langues présentes dans le JSON seront importées.

Réécrire database.py avec SQLAlchemy

Remplacer les requêtes SQLite brutes par SQLAlchemy. main.py ne change pas — même API, même résultat, nouvelle base.

Scaffolder le frontend Next.js

Remplacer l'HTML monolithique par Next.js + TypeScript. Router, composants (ExpressionCard, SearchBar, FranceMap), pages par expression / tag / carte.

Connecter Supabase (prod)

Avec l'URL fournie, configurer la variable DATABASE_URL et appliquer les migrations sur la base cloud. Aucun changement de code — juste la connexion.
