Les 4 problèmes identifiés
1. Pagination Python, pas SQL
Critique · database.py:258

Dans search_expressions(), PostgreSQL retourne toutes les lignes correspondantes, et c'est Python qui découpe avec un slice. Le paramètre limit/offset n'est pas transmis à la base — c'est de la pagination cosmétique.

all_results = exact + semantic # ↑ fetchall() a déjà tout chargé en mémoire Python return all_results[offset:offset + limit], len(all_results) # ↑ slice Python ≠ LIMIT/OFFSET SQL

Avec 500 expressions aujourd'hui : invisible. Avec 10 000 expressions et une recherche sur "pied" : PostgreSQL charge des milliers de résultats dans la mémoire Python à chaque requête. C'est le problème le plus structurant à mesure que tu enrichis la base.

Déclencheur : refactorer quand la base dépasse ~3 000 expressions par langue. Nécessite de revoir la logique exact + semantic + merge côté SQL.
2. Indexes B-tree manquants sur les JOINs chauds
Corrigible maintenant · migration Alembic

Les indexes GIN ajoutés couvrent la recherche full-text. Mais les JOINs utilisés sur chaque page d'expression ne sont probablement pas indexés. Sans index, PostgreSQL fait un scan séquentiel de tables qui grossissent vite — content_translations est déjà à 18 000 lignes, objectif 50 000+.

3. ORDER BY RANDOM() sur toute la table
Corrigible maintenant · database.py:149

get_random_expression() utilise ORDER BY RANDOM() LIMIT 1. PostgreSQL génère un nombre aléatoire pour chaque ligne de la table avant de trier. À 6 000 expressions c'est invisible. À 50 000 expressions c'est une requête lente à chaque "Expression du moment".

-- Actuel : scan + tri de toute la table ORDER BY RANDOM() LIMIT 1 -- Fix : récupérer un ID aléatoire d'abord, puis charger l'expression SELECT id FROM expressions ORDER BY RANDOM() LIMIT 1 -- puis : SELECT ... WHERE e.id = :random_id -- Ou mieux : TABLESAMPLE BERNOULLI(1)
Action : corriger en même temps que les indexes. ~15 min.
4. Sous-requête corrélée _EXCLUDE_PHRASEBOOK répétée partout
Atelier requis · database.py:62

La constante _EXCLUDE_PHRASEBOOK est injectée dans toutes les requêtes. C'est une sous-requête corrélée : elle s'exécute une fois par ligne de la table principale. À 10 000 expressions, c'est 10 000 mini-requêtes à chaque appel.

-- S'exécute N fois pour N expressions : AND NOT EXISTS ( SELECT 1 FROM expression_tags et_pb JOIN tags t_pb ON t_pb.id = et_pb.tag_id WHERE et_pb.expression_id = e.id AND t_pb.slug = 'phrasebook' )

La solution propre est d'ajouter une colonne is_phrasebook BOOLEAN DEFAULT FALSE directement sur expressions, indexée. C'est un changement de schéma + migration de données.

Déclencheur : à planifier en atelier. Pas urgent avant 5 000 expressions.

Atelier à planifier — Performance DB

  • Refonte pagination search_expressions — passer le LIMIT/OFFSET à SQL, pas Python. Le vrai défi : gérer le merge exact + semantic en SQL, et adapter le comptage total sans charger tous les résultats. Impacte aussi l'infinite scroll côté frontend.
  • Colonne is_phrasebook — décider si on l'ajoute maintenant (simple migration + backfill) ou si on supprime les expressions phrasebook plutôt que de les cacher. Chaque option a des conséquences sur le mode apprentissage/jeu en V4.
  • Trigger upgrade Neon — définir les seuils : à partir de quand on passe au plan payant (compute, stockage, connexions simultanées). À définir avant d'avoir des vrais utilisateurs en simultané.
Déclencher cet atelier quand la base approche les 3 000 expressions par langue, ou avant de lancer une campagne de croissance.
